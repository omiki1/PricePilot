# 数据库与降价监控

## V2 的保存与提醒门槛

数据库中新增 marketplace、destination、buyer_context_hash、currency、data_mode 和来源许可配置。image_url / affiliate_url 是来源字段；只在许可范围内缓存，不把远程图片自动落成本地长期副本。表设计不等于允许保存任何来源的所有字段。

真实平台的历史保存、内容分析与提醒必须按 [Amazon/JD接入说明](../app/ai/tool/Amazon与京东接入.md) 执行。live_showcase 关闭整个站点的追踪/历史/提醒；demo_full 仅存自建样本并生成模拟通知；live_full 需要站点与来源双重许可。不能只对 Amazon 禁用提醒却默认同站点其他平台都可开启。

## 先决定一套业务主库

为贴近参考项目，默认 MySQL + 现有 PyMySQL 经验。你也会 PostgreSQL，可以在 Day 1 选择 PostgreSQL 替换主库；后续所有“业务数据库”均指你选定的这一套，不需要双写。Redis 和 Neo4j 的加入时机见 [技术栈选择](技术栈选择-Redis-PostgreSQL-Neo4j.md)。

下面给出逻辑表和约束，末尾补充关键 SQL 与 Python 参考片段。金额统一定点精度；所有时间按 UTC 保存，页面转为用户时区，并显示时区。所有查询与写入采用参数绑定，不让模型自由生成并执行 SQL。

## 业务实体

| 表 | 关键字段 | 约束 / 用途 |
|---|---|---|
| users | id、通知地址、验证状态 | 可以先用单用户演示身份；对外服务时必须建立认证 |
| products | id、品牌、型号、规格、地区、成色、套装、保修、规范版本 | 只有规格完整后才能生成可靠的身份键；未知项不能强行唯一合并 |
| offers | id、product_id、source、seller、source_sku_id、url、规格指纹 | 来源 SKU 及变体组合唯一；保留商家差异 |
| evidence | id、offer_id、来源、摘录/存储引用、observed_at、data_mode | 可回指报价/评论证据，不存账号凭证 |
| price_history | id、offer_id、observed_at、item_price、payable_amount、cashback、currency、eligibility、freshness、规则版本、证据引用、buyer_context_hash、采样批次 | 追加快照；同报价同采样批次唯一，失败记录不伪装有效价格 |
| review_samples | id、product_id、来源评论 ID、内容摘要、时间、去重标识 | 保存支撑结论所需证据，避免重复计数 |
| watch_list | id、user_id、product_id、target_payable、currency、destination、marketplace、buyer_context、监控范围、status、armed、generation、last_checked_at、next_check_at | 记录同款限制、提醒规则和用户确认的资格 |
| notification_log | id、watch_id、generation、quote_id、dedup_key、status、attempts、sent_at、error | dedup_key 唯一，发信前先登记待发送记录 |

watch 默认跟踪指定产品规格在已接入来源中的合格最低付款金额；如果用户选择只跟踪某店铺，则监控范围固定到 offer_id。收藏不等于订阅邮件：先收藏，再明确设阈值并开启提醒。

## 价格历史要保存什么

保存可重现的快照：当时价格、优惠明细、适用资格、地区、运费、规则版本与证据。不能只存最终一个数字。历史查询要过滤相同资格口径，不能拿新人价与普通价拼成一条曲线。

同一 source SKU 后来变化规格时，停止原商品监控或标为需确认；不能把新规格价格记到旧产品下。

## 单实例监控流程

第一版单独运行一个监控工作进程；默认每 30 分钟检查一次，实际频率遵守来源配额并可调整。手动“立即检查”与定时检查走同一处理入口。

1. 读取到期且 active 的监控项，数据库原子认领，避免同一轮重复处理。
2. 获取最新报价和库存，重新核对规格、优惠资格与地区；不能只读过期缓存。
3. 计算付款金额，追加价格快照；只有 fresh、verified、eligible、费用完整、有货的结果继续。
4. 比较 payable_amount 与 target_payable；返现后成本不参与默认阈值判断。
5. 达阈值且 armed 时，在同一数据库事务内创建唯一通知记录并将该触发代次设为已触发。
6. 发信工作读取 pending 记录，发送后写 sent；暂时失败保持可重试并记录错误。
7. 更新检查时间。每项失败不阻断其他监控项。

## 去重和再次提醒

默认在创建监控时 armed。低于阈值后只提醒一次；持续低价不重复发。后续有一次新鲜合格价格回到阈值之上，才重新 armed 并递增 generation；再跌破才再次提醒。修改阈值视为新一轮订阅，先重置状态并复查。

dedup_key 由 watch_id 与 generation 组成，数据库唯一约束防重复任务。发送失败重试原 notification_log，不新增一封逻辑通知。

SMTP 无法仅靠本地日志保证绝对恰好发送一次：如果服务器接受邮件后进程崩溃，本地可能尚未记 sent。保留固定 Message-ID 并将不确定状态标为 unknown_delivery，第一版由人工确认或谨慎重试；不要承诺完全消除这种极小窗口内的重复。

## 邮件内容

产品完整规格、当前付款金额、目标金额、优惠条件、采集时间、来源链接、停止提醒入口。使用固定模板，收件人来自用户确认的通知地址，不采用网页或模型输出的地址。

第一版只向开发者自己的已验证测试邮箱发送；演示模式生成模拟通知日志，页面标注“测试提醒，未发送真实邮件”。用户需主动开启真实提醒。

## 数据验收

业务数据服务重启后仍在；同一采样不重复写；别人的 watch_id 不可读写；重复触发只生成一条通知；发信失败可以恢复；过期价、缺运费、条件会员价不会触发普通用户提醒。

## 参考代码 1：提醒状态机（纯逻辑模块）

目标：`app/jobs/price_monitor.py` 内的规则部分。依赖统一 PriceQuote。只返回决策，不连接数据库、不发邮件；持久化时必须在同一事务中保存 next_watch 和通知记录。

```python
from dataclasses import dataclass, replace
from datetime import datetime
from decimal import Decimal
from app.ai.agent.multi_agent.schema.shopping_schema import PriceQuote

@dataclass(frozen=True)
class WatchMemory:
    watch_id: str
    target: Decimal
    currency: str
    armed: bool = True
    generation: int = 0

def advance_watch(watch: WatchMemory, quote: PriceQuote, now: datetime,
                  site_enabled: bool, source_enabled: bool):
    if not site_enabled or not source_enabled:
        return watch, None
    if (quote.verification_level != "verified" or quote.freshness != "fresh"
            or quote.payable_amount is None or now >= quote.valid_until
            or quote.currency != watch.currency):
        return watch, None
    if quote.payable_amount > watch.target:
        if watch.armed:
            return watch, None
        return replace(watch, armed=True, generation=watch.generation + 1), None
    if not watch.armed:
        return watch, None
    key = f"{watch.watch_id}:{watch.generation}"
    return replace(watch, armed=False), {
        "dedup_key": key, "quote_id": quote.quote_id,
        "payable_amount": str(quote.payable_amount),
    }
```

调用前还必须确认当前快照对应此监控的 product_id、目的地、资格和库存。WatchMemory 是便于验证状态转换的最小对象，不是完整数据库模型。真实入口验证目标金额有限非负、用户归属和用途许可。

## 参考代码 2：通知去重约束（MySQL 结构示例）

下面只展示关键约束。watch_list 等表按上文补齐，时间由应用写入 UTC。选择 PostgreSQL 时调整类型和迁移脚本，不同时运行两种主库。

```sql
CREATE TABLE notification_log (
    id VARCHAR(36) PRIMARY KEY,
    watch_id BIGINT NOT NULL,
    generation INT NOT NULL,
    quote_id VARCHAR(36) NOT NULL,
    status VARCHAR(32) NOT NULL,
    attempts INT NOT NULL DEFAULT 0,
    created_at DATETIME(6) NOT NULL,
    sent_at DATETIME(6) NULL,
    UNIQUE KEY uq_watch_generation (watch_id, generation)
);
```

## 参考代码 3：参数化更新（仓储片段）

未来 product_repository.py；conn 为调用方管理的 PyMySQL 事务连接。这里不 commit，便于和通知登记放在同一事务里。对外接口不能允许客户端任意传 next_generation，应由锁定记录上的状态机计算。

```python
def save_watch_state(conn, watch_id, user_id, armed, next_generation):
    with conn.cursor() as cursor:
        cursor.execute(
            "UPDATE watch_list SET armed=%s, generation=%s "
            "WHERE id=%s AND user_id=%s",
            (armed, next_generation, watch_id, user_id),
        )
```

完整监控事务顺序：锁定并校验监控记录 → 验证快照口径 → 算决策 → 插入唯一通知 → 保存状态 → 提交。邮件由通知工作进程在事务外发送，不能持有数据库锁等待 SMTP。
