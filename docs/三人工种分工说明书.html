必须准备的三个细节（有实测数据支撑，最能加分）

  1. 为什么必须拦住空查询：Shopify catalog 是宽松语义检索，任何 query 都返回 50 条。实测 '鸣潮' → 返回一味中药 Rhizoma；'来一个1000以内的鸣潮周边' → 返回一本讲鸡的书 What the Chicken Knows。所以空/无意义检索词等于随机抽 50 个商品给模型推荐。
  2. 同一道闸为什么设两处：route_after_intent 拦在路由层，shopify_search_node 拦在发请求前。前者保证不「假装要检索」，后者保证不「真的发出去」——纵深防御，且第二处把降级暴露在日志里而不是伪装成「没货」。
  3. 预算语义的关键修正：BUDGET_MIN_RATIO 原为 0.1，把「1000 以内」误解成 900~1000 区间；实测 50 条候选全被判「低于下限」丢弃 → 候选 0 条 → 前端显示空白。改为 0 后只保上限，与 API 侧口径一致。

乙答辩时的核心论点 模型每一轮都必须重新知道「这个用户是谁」。记忆不是把历史塞进 prompt，而是四层不同时效、不同结构的信息，各有分工、各有降级。

必须准备的关键细节

  1. Checkpointer 与四层记忆的分工（高频追问点）：InMemorySaver 存的是图内运行状态，进程内、重启即失效；四层记忆是跨会话要记住的用户信息，落 Redis / PG / 向量库。两者职责不同，不能互相替代。
  2. 画像为空时推荐为什么不是空白：MODE_PROFILE 要求画像里至少有 frequent_categories 或 preferred_brands，否则降级到 MODE_FAVORITES（用收藏标题找同类），都没有才 MODE_SAMPLES（给 4 个示例问题、不给商品卡）。
  3. 缓存怎么保证不给人过期画像：缓存 key 里带画像指纹（profile_fingerprint），画像一变指纹就变，命中失效自动重查——不需要手写失效逻辑。
  4. L3 为什么必须换成本地中文嵌入：Chroma 默认的 all-MiniLM-L6-v2 是英文模型，对「只买黑色」「通勤戴」这类中文偏好的语义区分度差，且首次使用要联网下载 79MB。改为读 EMBEDDING_LOCAL_PATH 指向本地 bge-base-zh。

丙答辩时的核心论点 不能让模型编造价格理由。价格是一个有约束的合同对象、不是 float；每条结论都要能溯源到证据，溯源不到就在生成阶段拦掉。

必须准备的关键细节

  1. 为什么价格要建成合同对象：一次付款同时受券互斥组、券门槛、有效期、返现上限、币种约束。测试用例明确覆盖：负价/零价在合同层就拒绝、三位小数被拒绝、返现超过付款金额要报错、优惠大于商品金额被排除、now 必须带时区、有效期取选中券的最早截止。
  2. 「解释里查无出处的金额」怎么抓：报告中出现的金额必须能对应到证据 ID，对不上的会被判定为模型编造并揪出；同时纯统计数字（条数、比例）不会被误判成金额。
  3. 避雷项为什么是硬排除而不是降权：用户说「不要二手」是硬条件，降权意味着可能仍然推给他。且只做字面匹配、不命中近义词——宁可漏排也不误排。
  4. 贝叶斯平均为什么必要：score = (v/(v+m))·R + (m/(v+m))·C，m=50，同 IMDB Top 250 口径。解决「5.0 分只有 3 条评价」压过「4.6 分有 656 条」；无评价商品 score=None 并标注「暂无评价，无法评估」，而不是当 0 分。
  5. SSE 三种帧：text（增量文本）/ products（商品卡数据）/ done（结束，带 saved=false 表示答完但没存进历史）。断流有 stream_broken 错误码。
  6. 跨平台坑（最能体现动手能力）：Windows 上 uvicorn 硬编码返回 ProactorEventLoop，而 psycopg 异步模式要求 SelectorEventLoop，必然报错；最后改成同步驱动 + asyncio.to_thread。另有 passlib 1.7.4 与 bcrypt ≥ 4.1 不兼容（初始化即抛错且被 service 层吞掉，表现为「注册失败」），改为直接调 bcrypt。
